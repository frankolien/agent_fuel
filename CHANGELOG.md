## [Unreleased]

### Added

- **Backend — score engine (slice 3.5): `score_history`, Redis cache, 5-min sweep.** Every on-chain `ScoreComputed` event appends a row to `score_history` (PK `(agent, slot)` → replays no-op via `ON CONFLICT DO NOTHING`) and warms a Redis cache keyed `score:<agent>` with the new score and a 300-second TTL (matches the slice spec). The cache is only updated when the inserted row is the **new latest** — replaying an older score never clobbers the cached value with a stale one (subtle bug caught live and fixed). `score::latest(pool, cache, agent)` is the read path: Redis hit → fallthrough to `SELECT score FROM score_history ORDER BY slot DESC LIMIT 1` → backfill the cache. `score::sweep()` runs every 5 minutes (`tokio::spawn` interval task started in `main.rs`) and refreshes the cache for every agent with score history, so a Redis flush self-heals on the next tick instead of waiting for fresh events. Redis is optional in dev — `REDIS_URL` unset or unreachable degrades to "no cache, hit Postgres every time" with a startup warning instead of a hard failure (`ConnectionManager` is wrapped in `Option<ConnectionManager>` inside a cheap `Clone`able `ScoreCache`).
- **Backend — `score_history` migration `20260526000004_score_history.sql`.** Append-only `(id BIGSERIAL, agent TEXT, score INT, slot BIGINT, recorded_at TIMESTAMPTZ DEFAULT now())` with `UNIQUE (agent, slot)` and a `(agent, slot DESC)` index for the latest-score lookup. Real-DB smoke verified live: posting ScoreComputed at slot 300 then slot 400 writes both rows, agents mirror shows the latest (820), cache holds 820 with TTL 300; replaying the slot-300 payload returns 202 + leaves both row count and cached value unchanged.
- **Backend — Redis dep `redis = "0.27"`** (default-features off, `tokio-rustls-comp` + `connection-manager` for async + auto-reconnect). `agent_fuel_redis` container scaffold for local dev added to [docs/backend-local-dev.md](docs/backend-local-dev.md)'s teardown section.

- **Backend — mirror tables (slice 3.4): `agents`, `services`, `vaults`.** Per-entity snapshots that stay current via `mirror::refresh` after every webhook ingest. The events table is source of truth; mirror rows are recomputed from event history rather than incremented in-place, so a webhook replay or out-of-order delivery reconverges to the same row state instead of double-counting. `mirror::affected()` maps each event name to the pubkey(s) it touches (PaymentRecorded touches both agent and service; vault events all touch vault), and `refresh()` runs one `INSERT … ON CONFLICT DO UPDATE` per affected pubkey that rebuilds every field via aggregate subqueries against `events`. Counter fields whose events carry post-change totals (`new_total_deposited`, `new_total_spent`, `new_total_claimed`, `new_total_withdrawn`, `score`) use `MAX(...)` / `ORDER BY slot DESC LIMIT 1`; counters that need summing (`total_transactions`, `total_volume_usdc`, `services_used`) aggregate `PaymentRecorded` rows. `consecutive_success` is computed as the count of payments after the latest *unrevoked* negative feedback via a correlated `NOT EXISTS` join between `FeedbackGiven` and `FeedbackRevoked` on `payload->>'feedback'`. Mirror failures log but do not 500 the webhook — events are already persisted, so a subsequent webhook (or a future manual replay) reconverges the cache; we'd rather absorb a transient mirror error than make Helius retry the whole batch. Migration `20260526000003_mirror_tables.sql` carries the three tables plus `(owner)` and `(score DESC)` indexes on `agents`, `(category)` on `services`, and `(owner)` / `(agent)` on `vaults`. Smoke-test against the live DB: AgentInitialized + ServiceRegistered + 2× PaymentRecorded → agents.total_transactions=2, total_volume_usdc=3_500_000, services_used=1, consecutive_success=2; services.total_agents_served=1, total_volume_received_usdc=3_500_000; replaying the same payload leaves all counters unchanged.
- **Backend — event parser + `events` table (slice 3.3).** The webhook handler now decodes every Anchor `emit!` it finds in transaction logs and UPSERTs one row per event into `events`. Pipeline: `routes::webhooks::helius` → `parser::parse` (walks `meta.logMessages` or `transaction.meta.logMessages` per tx, tracks the invocation stack via `Program <id> invoke [n]` / `Program <id> success|failed:` lines, attributes each `Program data:` payload to the deepest active program) → `events::decode` (matches the 8-byte `sha256("event:<EventName>")[..8]` discriminator against the 15-event dispatch table; Borsh-deserializes the body in source-declaration order) → `persist::insert_events` (single `BEGIN` block, `INSERT ... ON CONFLICT (signature, log_index) DO NOTHING` so Helius's at-least-once retries no-op on the second delivery). HTTP status codes are now meaningful to the retry path: **202** on success, **500** on DB failure (Helius will retry — events table is source of truth, replay beats drop), **400** on malformed JSON (Helius can't fix this; we surface bad payloads instead of looping). Two-stage handler keeps the auth path testable without a `PgPool` via the `verify(expected, presented)` helper that returns `Option<HttpResponse>` for short-circuit.
- **Backend — `events` table (migration `20260526000002_events.sql`).** Schema: `signature TEXT × log_index INT × slot BIGINT × received_at TIMESTAMPTZ × program_id TEXT × event_name TEXT × payload JSONB`. PK on `(signature, log_index)` is the natural idempotency key (Helius replays absorb cleanly). Indexes: `slot DESC` (recent-activity reads), `(program_id, slot DESC)` (per-program scans for the score engine and dashboard), `(event_name, slot DESC)` (typed read paths), and a JSONB-pathops GIN for `WHERE payload @> '{"agent": "..."}'` filters without denormalising the payload into columns.
- **Backend — 15 Anchor event mirrors at `backend/src/events/{reputation,vault}.rs`.** Field order matches `programs/{reputation,credit_vault}/src/events.rs` verbatim (Borsh is positional — any reorder silently corrupts the JSONB payload, so the data-model.md tables are the contract). Reputation: `AgentInitialized`, `ServiceRegistered`, `PaymentRecorded`, `FeedbackGiven`, `ResponseAppended`, `FeedbackRevoked`, `ScoreComputed`. Credit vault: `VaultCreated`, `Deposited`, `Spent`, `Claimed`, `VaultFrozen`, `VaultUnfrozen`, `PolicyUpdated` (full 8-entry whitelist round-trips), `Withdrawn`. Discriminators are computed at first-use via `OnceLock` per type rather than hardcoded byte arrays, so renaming an event in source auto-updates the matched bytes — drift between event name and discriminator is impossible.
- **Backend — `events/types.rs` field-type wrappers.** Three Borsh-decodable newtypes that bridge raw on-chain bytes to indexer-friendly JSON: `PubkeyBytes` (32 bytes → base58 string, canonical Solana form), `Hash32` (32 bytes → lowercase hex without `0x`, matches the data-model.md receipt-hash convention), and `NameBytes` (UTF-8 zero-padded → trimmed string, with a hex fallback so malformed names can't crash the indexer).
- **Backend — discriminator-drift safety tests.** `discriminator_formula_matches_anchor_spec` pins the `sha256("event:<EventName>")[..8]` recipe against an independently-computed hash, and `discriminators_are_disjoint_across_events` proves no two events collide on the 8-byte prefix — either property breaking would silently mis-route or drop live events.
- **Backend — end-to-end smoke-encoded example.** `backend/examples/encode_sample_event.rs` round-trips through the public events API to produce a valid Helius-shaped payload from cli, so the full webhook → parse → decode → persist path can be exercised without waiting for an on-chain transaction (`cargo run --example encode_sample_event | curl -d @- …`).
- **Backend — `lib.rs` library surface.** Modules (`config`, `db`, `events`, `parser`, `persist`, `routes`, `state`) moved into a library crate so integration tests, examples, and future CLI helpers can re-use the pipeline without going through the HTTP layer. `main.rs` keeps only the entrypoint wiring.
- **Backend — Helius webhook receiver (slice 3.2).** `POST /webhooks/helius` ingests Helius enhanced-webhook payloads for the two on-chain program IDs. Helius authenticates with a static shared secret in the `Authorization` header (no scheme prefix, no HMAC) — we compare the presented value to `HELIUS_WEBHOOK_SECRET` using `subtle::ConstantTimeEq` so a probing attacker can't time-attack the secret one byte at a time. Three response paths: **503** when the secret isn't configured (fail-closed — the boot log already warned, but every request is double-checked; accepting anonymous webhooks would silently let any caller poison the indexer), **401** on missing or mismatched `Authorization`, and **202 Accepted** with the payload logged via `tracing` (parser arrives in slice 3.3). Auth + dispatch is factored into a pure `verify_and_log(expected, presented, body)` helper so the path is unit-testable without standing up `AppState` or a Postgres pool. New dep `subtle = "2"`. Backend now has **8 unit tests** covering all four response paths plus the constant-time-compare helper across equal / different-content / different-length / empty inputs.
- **Backend — Actix-Web + SQLx + Postgres skeleton (slice 3.1, Phase 3 begins).** New workspace crate at `backend/` (binary `agent_fuel_backend`). Boots Actix-Web on `BIND_ADDR` (default `127.0.0.1:8080`), opens an SQLx Postgres pool against `DATABASE_URL`, and applies embedded migrations from `backend/migrations/` on startup so a deployed image carries its schema with it (no separate `sqlx migrate run` on prod). Tracing via `tracing-subscriber` + `tracing-actix-web::TracingLogger`; `RUST_LOG` controls verbosity. Health is split deliberately: `GET /health/live` (no dependencies) feeds container liveness probes so a DB blip doesn't trigger a restart loop, while `GET /health/ready` runs `SELECT 1` and 503s on failure so load balancers can drain the instance. Bootstrap migration `20260526000001_init.sql` creates a single-row `schema_meta` table (`CHECK (id = 1)`) as a deployment marker — real domain tables (`events`, `agents`, `vaults`, `services`, `score_history`) arrive in Slices 3.3–3.5. `.env.example` lists every var Phase 3 will use (commented out for slices not yet shipped). Unit test for `/health/live` runs without Postgres; readiness verification needs a live DB and is deferred to Slice 3.2's webhook test plan.
- **Credit Vault program — `claim` instruction (slice 2.12, post-pay settlement).** Service-signed mirror of `spend` for after-the-fact settlement. Runs the same shared `policy::check_and_record_spend` ladder so the post-pay path can't drift from the pre-pay one, then gates on `policy.allow_post_pay` (`PostPayDisabled`, code 6009). Bumps both `vault.total_spent` (so claims count toward the lifetime/hourly ceilings on equal footing with spends) AND `vault.total_claimed` (so off-chain accounting can split the post-pay share). PDA-signed CPI transfer to the service's ATA; `service_token_account.owner == service.key()` enforced so an attacker can't claim into someone else's account. Emits `Claimed { vault, service, amount_usdc, new_total_spent, new_total_claimed, slot }`. LiteSVM tests: rejection when post-pay disabled, happy path with both counters bumped, shared lifetime ceiling with spend, rejection on frozen vault, rejection when signer ≠ destination ATA owner.
- **Credit Vault program — `withdraw` instruction (slice 2.11).** Owner reclaims USDC from the vault back into their own ATA via PDA-signed CPI transfer (same `invoke_signed` pattern as `spend`/`claim`). Bumps `vault.total_withdrawn` (`Overflow`-checked) and `last_active_slot`. **Deliberately works on frozen vaults** — freezing blocks `spend`/`claim` only; the owner can always recover their own funds. `ZeroAmount` rejects no-op withdrawals. The token program handles "can't withdraw more than the vault holds" — we don't duplicate. Emits `Withdrawn`. LiteSVM tests: happy path, works while frozen, zero-amount rejection, non-owner rejection, wrong-vault-token-account substitution rejection.
- **Credit Vault program — `update_policy` instruction (slice 2.10).** Owner rewrites the four limits, the `allow_post_pay` flag, and the entire 8-slot whitelist in one call. **Does not touch `hourly_window_start_slot` / `hourly_window_spent_usdc`** — limit changes apply forward; in-flight windows keep their running totals measured against the new ceiling. Emits `PolicyUpdated` carrying the complete new state so indexers don't need to read the policy account back. LiteSVM tests: full-rewrite happy path (asserts window counters survive), non-owner rejection.
- **Credit Vault program — `freeze_vault` + `unfreeze_vault` instructions (slice 2.9).** Two separate instructions rather than a toggle, so the caller's intent is explicit and the indexer sees distinct `VaultFrozen` / `VaultUnfrozen` events. Idempotent flips are rejected: `freeze_vault` on an already-frozen vault returns `AlreadyFrozen` (6007); `unfreeze_vault` on an unfrozen vault returns `NotFrozen` (6008). This forces callers to handle ownership errors at the call site rather than silently no-oping. LiteSVM tests: round-trip, double-freeze rejection, unfreeze-when-unfrozen rejection, non-owner rejection.
- **Credit Vault program — `spend` instruction with all six policy checks (slices 2.3 – 2.8).** Agent-signed; transfers USDC from the vault's PDA-owned ATA to a service's ATA via PDA-signed CPI (`invoke_signed` with `[b"vault", owner, agent, bump]` seeds). The recipient service is read implicitly from `service_token_account.owner` — saves an instruction arg and an extra check. Policy ladder runs in shared `policy::check_and_record_spend` (reused by `claim` so the two can't drift on auth surface): **(1)** `!vault.frozen` → `Frozen` (6002); **(2)** `amount_usdc > 0` → `ZeroAmount` (6001); **(3)** whitelist membership (no-op if every slot is `Pubkey::default()`, else recipient must match one of the non-default entries) → `NotWhitelisted` (6003); **(4)** `amount_usdc <= per_tx_limit_usdc` when limit > 0 → `PerTxLimitExceeded` (6004); **(5)** rolling hourly window: reset start_slot + spent_usdc to current values when `elapsed >= SLOTS_PER_HOUR` (9,000), then check `window_total + amount <= hourly_limit` → `HourlyLimitExceeded` (6005); **(6)** `vault.total_spent + amount <= lifetime_limit` when limit > 0 → `LifetimeLimitExceeded` (6006). All math `checked_add` → `Overflow`. The hourly-window reset uses elapsed-only logic (no `start_slot == 0` sentinel) so a legitimate "spend at slot 0" in tests or at genesis behaves correctly — same class of bug we fixed in the reputation rate-limit. Emits `Spent`. **10 LiteSVM tests** cover happy path, each rejection branch, an "exactly at limit" success case, and window reset after `warp_to_slot`. Non-agent signer rejection via `has_one = agent`.
- **Credit Vault program — `SpendPolicy` schema change (whitelist switched from merkle root to fixed array).** `whitelist_root: [u8; 32]` is now `whitelist: [Pubkey; 8]` (256 bytes). Pre-deployment so no migration concern. Rationale: 8 entries covers realistic v1 vault usage (one agent + a handful of services); merkle would save 224 bytes but cost an off-chain proof builder, a per-spend proof argument, and ~30 lines of in-program hash math. When real-world whitelists outgrow 8 entries, we add merkle as its own slice. `SpendPolicy` size 186 → 402 bytes; padding still 64.
- **Credit Vault program — `policy.rs` shared check-and-record helper.** Single home for the six-check ladder so `spend` and `claim` can't drift on the authorisation surface. Caller does its own SPL transfer, per-caller counter bumps (e.g., `claim` also bumps `total_claimed`), `last_active_slot`, and event emission. Mutates `vault.total_spent` and the policy's rolling-window fields in place.
- **Credit Vault program — `deposit` instruction (slice 2.2).** Owner moves USDC from their own ATA into the vault's PDA-owned ATA via `spl_token::transfer` CPI; bumps `total_deposited` (checked-add → `Overflow` / code 6000) and `last_active_slot`. Auth is enforced two ways belt-and-braces: Anchor `has_one = owner` on the vault PDA *and* the vault's PDA seeds re-derive from `vault.owner` / `vault.agent`. The vault token account is pinned by `constraint = key == vault.vault_token_account` (not re-derived from ATA seeds — wasted CU for an identical result), blocking destination-substitution attacks. The owner's source ATA is pinned by `mint == vault.usdc_mint`, blocking wrong-mint deposits. `ZeroAmount` (6001) rejects zero-amount calls explicitly even though the SPL transfer would no-op them — saves caller debugging time. **Allowed on frozen vaults** by design: freeze blocks `spend`/`claim`, not funding (owners may legitimately top up before unfreezing). Emits `Deposited { vault, owner, amount_usdc, new_total_deposited, slot }` carrying the post-bump total so indexers don't have to re-read the vault. LiteSVM tests cover happy path, accumulation across three deposits, zero-amount rejection, non-owner signer rejection (`has_one`), substituted vault-token-account rejection, and wrong-mint rejection. New errors module with `Overflow` (6000) and `ZeroAmount` (6001).
- **Credit Vault program — Phase 2 begins.** `CreditVault` (250 B) and `SpendPolicy` (186 B) PDAs plus `create_vault` instruction. One vault per `(owner, agent)` pair — seeded `[b"vault", owner, agent]`, with the policy at `[b"policy", vault]`. `create_vault` initialises both PDAs and a PDA-owned USDC Associated Token Account in one transaction. Owner-only signature: the agent doesn't consent because the vault is the *owner's* money — contrast with `initialize_agent` (dual-sig) where the PDA is the agent's identity and could be squatted. The mint is **not** hardcoded; the owner passes whatever mint they're funding with (USDC in production, a locally-minted SPL token in LiteSVM tests) and the vault stores it for cross-instruction sanity checks. The four spend-policy fields (`per_tx_limit_usdc`, `hourly_limit_usdc`, `lifetime_limit_usdc`, `allow_post_pay`) are set at creation; rolling-window counters (`hourly_window_start_slot`, `hourly_window_spent_usdc`) are initialised to zero. The `whitelist_root: [u8; 32]` defaults to all-zero — the "allow any service" sentinel that slice 2.5 will override. `Box<Account>` on `CreditVault`, `SpendPolicy`, and the `TokenAccount` keeps `try_accounts` under Solana's 4096-byte stack frame. No custom errors yet — Anchor's `init` catches re-creation and `Signer` catches missing signatures. Emits `VaultCreated`. LiteSVM tests cover happy path (asserts every vault + policy + ATA field), re-creation rejection, missing-owner-signature rejection, and distinct-`(owner, agent)`-pairs-get-distinct-PDAs. New dev-deps: `spl-token = "8.0"`, `spl-associated-token-account = "7.0"`. LiteSVM's `with_default_programs()` (loaded by `LiteSVM::new()`) already includes both program runtimes, so no extra `add_program_from_file` calls are needed.
- **Reputation program — `compute_score` instruction (slice 6, Phase 1 exit).** Permissionless: any wallet may invoke for any agent — the score is a pure function of public on-chain state, so gating it would just add friction. Reads the aggregated counters on `AgentProfile` and writes `reputation_score: u16` in basis points `[0, 1000]`. Five-component piecewise formula: **Volume** (250 pts, bracketed on `total_transactions`), **Diversity** (200 pts, `50 × min(services_used, 4)`), **Streak** (150 pts, `10 × min(consecutive_success, 15)`), **Tenure** (150 pts, bracketed on `current_slot − first_active_slot` — *age from registration*, not active span, because a long-lived quiet identity is harder to fake than a flurry of recent activity), and **Feedback** (250 pts, linear in `1 − active_negative_feedback_count / total_feedback_count`, neutral 100 when no feedback yet). All math is integer + saturating; weights are statically asserted at compile time via `const _` so a future edit that shifts a cap without re-deriving the weight breaks the build. Emits `ScoreComputed`. LiteSVM tests cover brand-new neutral baseline (100), permissionlessness (stranger signs), 100% negative feedback collapsing the feedback bracket, ceiling assertion via `warp_to_slot` past 30 days plus four positive feedbacks across distinct services, and idempotence for fixed inputs. Seven unit tests in `compute_score.rs` cover each component bracket independently. Score formula **is** the slice — no custom errors, the function is total over its inputs.
- **Reputation program — `give_feedback` rate-limit enforcement (slice 5d).** At most one feedback per `(service, agent)` per `FeedbackRecord::FEEDBACK_RATE_LIMIT_SLOTS` (216,000 slots ≈ 24h at 400ms/slot). Field-placement decision: the rate-limit state lives on the existing `AgentServiceLink` rather than a side PDA — the link already represents the per-pair relationship, give_feedback already passes it, and no new account or rent is needed. `AgentServiceLink` gains `last_feedback_slot: u64` and `has_received_feedback: bool` (size 169 → 178 bytes; 64-byte padding preserved). The bool is **not** a `last_feedback_slot == 0` sentinel — real feedback can land at slot 0 at genesis or in test environments, so the slot value alone can't distinguish "never" from "at the start". `give_feedback`'s handler reads the flag, computes `slot.saturating_sub(last_feedback_slot)`, and raises `FeedbackRateLimited` (6009) if the window has not expired. On success it sets both fields and emits no new event (the existing `FeedbackGiven` carries the slot). LiteSVM tests cover (a) second feedback inside the window is rejected and no `FeedbackRecord` is left behind, and (b) second feedback after `warp_to_slot` past the window succeeds and `total_feedback_count` reaches 2.
- **Reputation program — `revoke_feedback` instruction.** The original feedback-giver retracts its own feedback. Authorisation is enforced through two independent checks that both have to pass: (1) the `service_registry` account is PDA-derived from `[b"service", service.key()]` (so the signer must be the registry's authority), and (2) `has_one = service_registry` on `feedback_record` (so the feedback must reference *this* registry). Together those make it structurally impossible for any other service to revoke. The handler then rejects double-revoke via `feedback_record.revoked == false`, raising `AlreadyRevoked` (code 6008). When the revoked feedback had `value < 0`, `agent_profile.active_negative_feedback_count` is decremented with `checked_sub` — an underflow here would indicate prior state corruption and surfaces as `Overflow` (6000). `consecutive_success` is deliberately **not** restored on revoke; the streak field's semantic is "successes since the last recorded negative event" and we don't store enough history to rewind it correctly. Emits `FeedbackRevoked` carrying `was_negative` so indexers can update aggregates without re-reading the FeedbackRecord. LiteSVM tests cover negative-feedback decrement, positive-feedback no-op on the negative count, double-revoke rejection, wrong-service rejection (with the attacker registered as their own service to exercise the `has_one` path specifically), and missing-signature rejection.
- **Reputation program — `append_response` instruction.** Either the agent (authority) or its owner can attach a single response URI + hash to an existing `FeedbackRecord`. `has_one = agent_profile` on the feedback account and a `responder.key() == agent_profile.owner || responder.key() == agent_profile.authority` constraint enforce the authorisation gate; mismatches surface as `UnauthorizedResponder` (code 6006). The handler then rejects re-append via `feedback_record.has_response == false`, raising `AlreadyHasResponse` (6007). Mutates the existing 512-byte `FeedbackRecord` (no new PDA, no rent) — `response_uri`, `response_hash`, `has_response`, and `last_modified_slot` are set; `agent_profile.last_active_slot` is bumped. Emits `ResponseAppended`. Deliberately does **not** block responses to revoked feedback — that filtering is the score engine's job in slice 6. LiteSVM tests cover both signer paths (owner, authority), third-party rejection, double-append rejection, and missing-signature rejection.
- **Reputation program — `give_feedback` instruction + `FeedbackRecord` PDA.** Service-signed feedback for a specific payment. Mints a 512-byte `FeedbackRecord` PDA seeded `["feedback", payment_receipt_hash]`, so at most one feedback can ever be filed per payment (second attempt fails with `AccountAlreadyInUse`). The ERC-8004 anti-self-rating check from [ADR-0004](docs/decisions/0004-dispute-and-feedback-model.md) is enforced on-chain as Anchor `constraint`s on `agent_profile`: `signer != agent_profile.owner` and `signer != agent_profile.authority`, both surfacing as `SelfRating` (code 6003). Feedback is bound to a real payment by walking the chain `payment_receipt_hash → ReceiptUsed → AgentServiceLink`; a mismatch raises `ReceiptMismatch` (6004). `value` is an `i8` constrained to `[-100, 100]` — outside that range raises `InvalidFeedbackValue` (6005). Negative feedback (`value < 0`) bumps `active_negative_feedback_count` and resets `consecutive_success` to zero on the agent. Pre-allocates the `response_uri` / `response_hash` / `has_response` / `revoked` fields that slices 5b and 5c will populate. Emits `FeedbackGiven` carrying agent, service, feedback PDA, receipt hash, value, tags, and slot. LiteSVM tests cover positive happy path, negative streak reset, self-rating rejection (by authority and by owner — separate keypairs), out-of-range value rejection, double-feedback rejection, and missing-signature rejection.
- **`Box<Account>` on `AgentProfile` and `FeedbackRecord` in `GiveFeedback`.** Required to keep `try_accounts`'s stack frame under Solana's 4096-byte limit — the combined account footprint (321 + 171 + 169 + 113 + 512 = 1,286 bytes plus deserialization scratch) overflowed without it.
- **Reputation program — `record_payment` instruction + `AgentServiceLink` and `ReceiptUsed` PDAs.** Service-signed instruction that records an x402 payment. Bumps `total_transactions`, `total_volume_usdc`, `consecutive_success`, and `last_active_slot` on `AgentProfile`; bumps `total_volume_received_usdc` and `last_active_slot` on `ServiceRegistry`. `AgentServiceLink` is a per-pair marker (169-byte PDA seeded `["link", agent_profile, service_registry]`, created via `init_if_needed`) that ensures `services_used` and `total_agents_served` increment exactly once per unique `(agent, service)` pair. `ReceiptUsed` is a per-receipt-hash marker (113-byte PDA seeded `["receipt", payment_receipt_hash]`, created via `init`) that enforces single-use of every payment receipt hash globally across the program — replay of the same hash, including across different pairs, fails with `AccountAlreadyInUse`. Service-signed instead of backend-signed in v1 — the service is the natural attester of the off-chain x402 settlement; a backend co-signer can layer on later without a schema break. Signer-to-registry binding is enforced through the PDA seed (`["service", service.key()]`) rather than a `has_one`, so an attacker signing with their own key cannot drive someone else's registry. All counter mutations use `checked_add` and surface as `ReputationError::Overflow` (code 6000). Other new errors: `ServiceInactive` (6001), `ZeroAmount` (6002). Emits `PaymentRecorded` carrying the payment receipt hash for off-chain audit. LiteSVM tests cover happy path, repeat-pair no-double-bump, distinct-services bump, zero-amount rejection, missing-signature rejection, wrong-signer rejection, receipt-replay rejection, and cross-pair receipt-collision rejection.
- **`anchor-lang/init-if-needed` feature** enabled on the reputation crate. Required by `AgentServiceLink`'s lazy init; the link's read-after-init paths are guarded by a `Pubkey::default()` sentinel so the init-if-needed footgun (passing a pre-existing account) doesn't apply.
- **Reputation program — `ServiceRegistry` PDA and `register_service` instruction.** Per-service registration with `name: [u8; 32]`, `category: ServiceCategory` (`DataFeed` / `Compute` / `Swap` / `Rpc` / `Other`), an `active` soft-delete flag, and running totals. 171-byte account. Single-signature (no dual-sig analog needed — a service has no separate human owner; the wallet *is* the service).
